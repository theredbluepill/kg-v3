# Run statement — compiled-GEMM limits at our shapes (single GPU, ≤ 45 min)

- **Question (diagnostic, not training):** the rebuild's `_run_trunk` guard assumes the torch 2.9 Inductor max-autotune GEMM template goes wrong exactly when `M × 512 > 2³¹` (M = token rows). That number was extrapolated from one probe at width 1024. This run asks two things. (1) At our widths, where do compiled GEMMs start disagreeing with eager or faulting? (2) Does the real `KaggricultureTransformer` trunk on `kg/rebuild-model` stay correct everywhere the guard admits it, and raise or chunk everywhere it doesn't? A separate question: is the limit set by the input width K, the output width N, or max(K, N)? The source-reading audit predicts max(K, N).
- **Hypotheses and discriminating observations:**
  - **Input/output split:** `Linear(16→4096)` (N-only) and `Linear(4096→16)` (K-only) both go wrong just above M = 2¹⁹ = 524,288 → the limit is M·max(K,N). Only the K-only case goes wrong → the limit is input-side only.
  - **Our trunk widths:** `Linear(256→512)`, `Linear(512→256)` and the GELU MLP `256→512→256`. Compiled output matches eager (within the BF16 tolerance `|d| ≤ 0.02 + 0.02|ref|`) at M ≤ 4,194,304. It has bad rows or faults at M = 4,194,305 (L+1), L+4096 and 2L → the guard constant 512 is measured, not just inferred. A match above L means the limit is looser than predicted, or autotune picked cuBLAS; the generated code decides which.
  - **Head/q-k-v widths:** `256→256`, with L = 8,388,608. `768→256` (the planned actor_input_proj), with L = 2,796,202.
  - **Real trunk, packed path** (`force_flash_attn=True`): matches eager at 256 rows (sparse and dense), 5,914 and 5,915 dense rows, and exactly 4,194,303 packed tokens. Raises `ValueError` before any trunk call at 4,194,304 tokens, 5,916 dense rows and 11,830 dense rows. **Negative control** (guard patched off): wrong or faulting at 4,194,305+ tokens. This shows the guard is load-bearing and that the compare would have seen the corruption.
  - **Real trunk, padded path:** 5,916 rows splits into trunk calls [4,193,735, 709] and 11,830 rows into [4,193,735, 4,193,735], all matching eager. The negative control (no chunking) goes wrong at 5,916 or 11,830 rows.
  - Silent corruption is detected separately from faults, because every point compares against eager. It is not just "no crash".
