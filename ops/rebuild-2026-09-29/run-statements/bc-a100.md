# Run statement: BC warm start on the A100 pod (top-1 team, 7 days, 1 GPU)

- **Question.** Can a warm-start policy be trained by behavior cloning the
  leaderboard #1 team's winning seats over 2026-09-22..28 within the owner's
  whole-BC window ("train it within whole BC time 1.5-2h for 7 days"), and
  where does its held-out NLL bottom out? This is a selection run: it picks the
  checkpoint with the lowest held-out NLL. It does not test playing strength.
- **Inputs.**
  - Source: `kg/rebuild-bc-now`, the commit that adds this statement and the two
    1-GPU configs (its hash is recorded by `train_bc.py` in
    `bc_attempts.jsonl` and in the receipts). Trainer code is unchanged from
    `89ca39c` (the pod's `owl_rs` build is reused; no Rust change).
  - Data: `/workspace/kg-v3-bc-2026-09-29/shards-top1/` (the single-team
    dataset), manifest SHA-256
    `ba5fe1c417741c587473b5696a6ca55227240b394236948cb4f4f5c4ed9a3036`;
    507 train episodes / 182,273 turn rows, 16 validation episodes / 5,748
    rows, turn stride 2. The superseded mixed-winner `shards/` is not used.
  - Config: `configs/bc/kaggriculture_1gpu_eager.yaml` ->
    `configs/kaggriculture_1gpu_eager.yaml`.
- **Method.** One A100 80GB PCIe, plain `python scripts/train_bc.py` (world
  size 1 via `distributed_session`). Isaiah's 1-GPU rule: the 2-rank BC config's
  global batch is kept (rows_per_rank 256 x 2 ranks -> 512 on one rank,
  gradient accumulation 1; fall back to 256 x accum 2 only on OOM). Optimizer,
  LR schedule, seed, value_coef, eval cadence and patience are the 2-rank
  config's. **Deviation:** eager model (`rl.model_compile: none`), because the
  pod's NVIDIA driver 580.159.03 is not in the probed compile stack
  (`owl.model.compile_gemm`, 595.91.07) and `train_bc.py` refuses it; this
  costs throughput, not correctness. BF16 autocast and flash-attn 2.8.3 as
  configured. W&B: no key on the pod, so `--wandb-mode offline` into the run
  directory (telemetry outage stays visible; sync later if wanted).
- **Expected observation.** Held-out policy NLL falls from its step-0 value and
  either reaches a minimum then rises (L9 stop fires) or is still falling at the
  cap (then the cap, not the data, limited selection).
- **Stopping.** First of: best held-out NLL followed by the trainer's L9 stop
  (10 scheduled evaluations x 200 steps without improvement), `max_steps`
  100,000, the hard cap `--max-runtime-hours 2` (clock starts inside
  `train_bc` after data load and model build, so preflight replay counts), or
  a crash (diagnose once, fix only the obvious cause, relaunch).
- **Budget.** Pod 23f7xiz368x9jf at $1.66/h; about 2.5 h wall including data
  load, so about $4. No new billable resource.
- **Artifacts.** Pod run dir under `/workspace/kg-v3-bc-2026-09-29/run/`
  (`checkpoint_bc_best.pt` + `.json`, `bc_state.pt`, `bc_history.jsonl`,
  `bc_result.json`, `bc_attempts.jsonl`, configs, offline W&B), launch log in
  the same directory. Compact receipts (history, result, attempts, sidecar,
  log excerpt, SHA-256, GPU samples) copied to
  `ops/rebuild-2026-09-29/bc-a100-2026-09-29/`.
- **Safety.** Read-only on existing `/workspace` data; new outputs only under
  `/workspace/kg-v3-bc-2026-09-29/run/`; scratch under `/root`. No driver,
  CUDA or torch changes; no credentials printed or committed. The pod is left
  running after the run; the owner decides when to stop it.
