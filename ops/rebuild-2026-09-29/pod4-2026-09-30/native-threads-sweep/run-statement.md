# Run statement: 4-rank native_threads sweep (throughput diagnostic, recipe J, 10 iterations each)

**One line:** on pod `abl4mvr5w1mmn4` (4x RTX PRO 6000, source `7e87f54`, clean detached checkout), run recipe J at 4 ranks for 10 iterations (163,840 global env steps) with `env.native_threads` N in {2, 4, 8, 16}, then N=8 with per-rank NUMA binding, and pick the N with the highest complete-work game SPS over iterations 3-10 (ties within 3% go to the lower N); stop after the five rows, the first hard failure of a row (recorded as its result), or about 20 minutes of wall time.

- **Owner request:** "can you quickly test Lever 1 on 4-rank, what is the best option of native threads?" and "let's decide the native threads first." This is a throughput diagnostic, not training; no checkpoint from it is used, selected or ranked.
- **Question:** does the rollout on 4 ranks (64 envs per rank) become shorter as the Rust env's rayon pool grows, and where does it stop paying? Expected discriminating observation: native step ms per rank falls with N until the per-step work (64 envs) no longer splits usefully or the model forward dominates the rollout; game SPS then flattens.
- **Command (per row):** `torchrun --nproc-per-node 4 nt_probe.py scripts/run_ppo.py configs/kaggriculture_4rank.yaml /root/runs/sweep-<label> --load-model-weights /root/bc-best/checkpoint_bc_best.pt --load-model-weights-mode model_only --log-mode wandb --wandb-mode online --experiment-id kg-v3-native-threads-sweep --max-env-steps 163840 -o optimizer.muon_lr=0.0002 optimizer.adamw_lr=0.00001 rl.checkpoint_freq=10000000 env.native_threads=<N>`. `env.seed` stays at the config default, so every row plays the same games. BC best sha256 `fd854587…6f51`. `OMP_NUM_THREADS=1`; one shared `TORCHINDUCTOR_CACHE_DIR`/`TRITON_CACHE_DIR` so only the first row pays the full compile.
- **Instrumentation (`nt_probe.py`, outside the checkout):** observes only. It times `KaggricultureVectorizedEnv.step` per call (fence + native step + buffer publish, synchronous), and records after each `train_iteration` the trainer's own `time/*` and `perf/*` metrics, `train/player_step_total`, process CPU seconds per rank and machine-wide `/proc/stat` busy time. It refuses a W&B run that is not online. With `KG_NT_NUMA=1` it sets, before torch loads, the rank's CPU affinity to its GPU's NUMA node (GPU0/1 -> node 0 CPUs 0-63,128-191; GPU2/3 -> node 1 CPUs 64-127,192-255) and an `MPOL_BIND` memory policy to that node by the `set_mempolicy` syscall (`numactl` is not installed; nothing is installed).
- **Measures (iterations 3-10 only):** mean iteration seconds; game SPS = 8 x 16,384 / wall between the ends of iterations 2 and 10 on rank 0 (includes logging); learner-seat SPS = the rise in `train/player_step_total` over the same wall; rollout, teacher and update seconds; native step ms per rank; CPU cores used per rank and machine-wide CPU %; warnings.
- **nsys:** not used; this compares end-to-end rates across one config knob and does not attribute time inside a step.
- **Budget:** about 20 minutes at $8.36/h (about $3). No main run is launched. The pod is left running and idle.
- **Limits:** one 10-iteration sample per row, so run-to-run noise is not measured; the 3% tie rule absorbs some of it. Iterations 3-10 cover steps 128-640 of the first 720-step game, so no reset and no game end falls in the window, and the last 80 steps of a game are not sampled.
