# Kaggriculture configs follow Isaiah's scaling_6m recipe

These configs **deliberately align to Isaiah**, as the [[../decisions/recipe-choices-align-to-isaiah-without-owner-escalation|recipe Decision]] requires: every recipe choice resolves toward upstream `scaling_6m`, and only per-rank shapes change with the world size.

## What changed (rebuild Task 3.4)

- **`configs/kaggriculture_2rank.yaml`** (128 envs/rank, `segments_per_minibatch` 8, accumulation 1) **`configs/kaggriculture_4rank.yaml`** (64/4/1) and **`configs/kaggriculture_8rank.yaml`** (32/2/1, added 2026-09-29 for the owner's likely 8-rank main run; see the [[../decisions/start-multi-gpu-qualification-with-two-ranks|multi-GPU Decision]]). This is Isaiah's 6M multi-GPU division from `winner_ce_6m_4x5090.yaml` (his per-rank fit of the different `winner_ce_6m` recipe): divide `n_envs` and `segments_per_minibatch` by the world size and keep the global batch. His only 8-GPU config, `scaling_50m`, keeps 256 envs/rank instead, so it is not the precedent for a 6M global workload. Everything else is `scaling_6m`'s:
  - the Muon optimizer and the linear-warmup cosine schedule (1,000 / 400,000 steps; the global batch is unchanged, so nothing is rescaled);
  - the PPO coefficients (gamma 1, λ 0.9, clip 0.2, no value clip, `vf_coef` 2, `ent_coef` 1e-6, grad norm 10, `target_kl: null`, `per_player`, normalized advantages);
  - the last-best teacher (0.005 / 0.005, `teacher_segments_per_minibatch` 128, not divided, as in Isaiah's per-rank configs), 8 evaluation replays, `compile_mode: default`, BF16 and the trunk-compile defaults. The checkpoint cadence was `scaling_6m`'s 20M until the owner halved it to 10M on 2026-09-30 ([[../decisions/halve-the-kaggriculture-checkpoint-interval-to-10m-steps|cadence Decision]]); `test_ranked_config_optimizer_and_ppo_equal_scaling_6m` exempts that field and `test_checkpoint_interval_is_the_owners_half_of_scaling_6m` pins it.
- **Kaggriculture-only settings:** the env section (`obs_spec` schema 3, `hire_limit` 241, `reward_mode: win_loss`, and a provisional `native_threads: 2` that Task 6.1 measures) and the owner's economic shaping 0.2. The other reward coefficients are the reference branch's defaults, named as in its `rewards.py`, which plan C8 ports. The model is the existing `configs/model/kaggriculture.yaml`, which already forces FlashAttention. It is not renamed to the plan's `kaggriculture_gpu.yaml`, because model tests and docs cite that path.
- **BC fine-tune presets (2026-09-30):** `configs/kaggriculture_{2,4,8}rank_bc_finetune.yaml` are the ranked configs with both learning rates / 10 and nothing else changed (the 4-rank one was added with the bank presets); see the [[bc-fine-tune-presets-divide-both-learning-rates-by-ten|fine-tune preset Reference]]. The global-workload and per-rank-shape tests cover them.
- **Owner term A (2026-09-30):** every Kaggriculture config sets `econ_bank_weight: 0.0`, `econ_bank_scale: 100000.0` and `econ_bank_cap: 0.0` explicitly, which leaves rewards bit-identical. `configs/kaggriculture_{2,4,8}rank_bc_finetune_bank.yaml` copy their recipe-J preset with both LRs halved and the bank term on (1.0 / 100,000 / .25, `terminal_scale` .5). This is an owner deviation, not an Isaiah alignment; see the [[../decisions/add-absolute-own-bank-shaping-and-halve-the-recipe-j-learning-rates|term A Decision]]. The workload, shape, cadence, teacher, diff and startup-headroom tests cover them.
- **Local CPU configs:** `configs/kaggriculture.yaml` (2 envs, spm 1, FP32, no compilation, no replays) and the tiny `configs/model/kaggriculture_cpu.yaml` (width 16, depth 1, FlashAttention off) are for Task 3.5. They use the same optimizer and PPO coefficients.
- **Startup workload check** (`python/owl/model/kaggriculture_workload.py`, from the GEMM-limit audit in the [[compiled-gemm-template-overflows-above-2-21-rows|overflow Reference]]):
  - `ppo_forward_workloads` derives each forward's per-rank seat rows: rollout `n_envs × 2`, minibatch `spm × horizon × 2`, teacher chunk `min(teacher_spm, n_envs) × horizon × 2`, and evaluation `n_envs × 2`. A BC caller adds its own `ForwardWorkload`.
  - `check_workload_headroom` divides these by the model's own `rows_per_chunk` (709 padded tokens × width 512, giving 5,915 rows) and `head_rows_per_chunk` (11,096). It raises when one row cannot fit either limit or a workload is empty. Head calls are exact. Trunk figures assume full padding, so trunk calls are an **upper bound** and trunk headroom a **lower bound**: the packed path plans chunks from actual token counts (16,384 rows of 300 tokens need 2 packed chunks, not 3).
  - **At startup:** `scripts/run_ppo.py` calls `_check_model_workload` once the per-rank shapes are final (after runtime-GPU adaptation, fresh or resume) and before the run directory, env or model exist. The teacher chunk is omitted when `teacher_mode` is unset. The main process prints one `GEMM workload headroom …` line per workload. Isaiah's Orbit models do not chunk, so they are skipped.
- **Kaggriculture env in `FullConfig`** (Codex r2 P1):
  - `python/owl/kaggriculture/config.py` adds `KaggricultureEnvConfig` (`n_envs`, the Kaggriculture obs/action specs, `reward_mode: win_loss` only, `reward_shaping`, `pin_memory`, `native_threads ≥ 1`; Isaiah's `two_player_weight` is an unknown key) and, in Task 3.4, a `KaggricultureRewardConfig` with the reference branch's field names and defaults. Since Task 1.5 the single definition is `owl.kaggriculture.rewards.KaggricultureRewardConfig`: all coefficients (six, nine since owner term A) are required, finite and nonnegative (no defaults), enabled caps must sum strictly below one, positive `econ_shaping` needs a positive `econ_cap` and a positive binary64 product with the starvation or drought weight, and a positive ineffective weight needs a positive ineffective cap (see the [[reward-reuse-preserves-objective-and-critic-semantics|reward Reference]]). The shipped YAML files set all six explicitly (`econ_ineffective_cap` 0.1 in every ranked config).
  - `python/owl/train/config.py`: `FullConfig.env` is `GameEnvConfig`, Isaiah's `EnvConfig` or `KaggricultureEnvConfig`, chosen by a callable discriminator on `env.obs_spec.obs_spec` (absent means Orbit, since Isaiah's `EnvConfig` has no game tag). The validator pairs the Kaggriculture env and model in both directions, requires `rl.gamma=1.0` and rejects `value_loss: winner_ce` for Kaggriculture (after the integration merge it then applies Tasks 3.2/3.3's `_validate_kaggriculture_training`, which adds `value_loss: mse` and `ppo_clip_mode: per_player`; see the [[evaluation-and-truncation-follow-the-kaggriculture-objective|evaluation and truncation Reference]]), and runs Isaiah's Orbit cross-checks unchanged in `_validate_orbit_constraints`. This replaces the Task 3.1 model-side rejection.
  - `require_orbit_env(env, context=...)` narrows to `EnvConfig` and raises an explicit `RuntimeError` for Kaggriculture. `scripts/run_ppo.py` runs the workload check, then the compile-stack check, then an explicit Kaggriculture guard that raises "run_ppo cannot run Kaggriculture yet: Task 3.1 rollout storage and action mapping are not implemented" before the run directory exists; `require_orbit_env` follows for Orbit and guards the other Orbit-only sites (model build, teacher specs, the Orbit branch of the evaluation env, which builds Kaggriculture games through `owl.game.create_env` since Task 1.5); `scripts/benchmark_checkpoints.py` uses it through a `LoadedCheckpoint.env` property and at checkpoint load.
- **Tests:** `tests/scripts/test_run_ppo.py` drives `run_ppo.main` from the shipped YAML through the real `FullConfig.from_file`; only the release-build check, torch setup and the distributed session are stubbed, and the run-dir, env and model steps are fail-if-reached sentinels. A `-o model.embed_dim=2097152 model.n_heads=65536` override fails the check with no headroom lines and no run directory. The 2-, 4- and 8-rank configs print the headroom lines and then stop with the explicit not-wired error, with no run directory. A real resume directory saved at 2 ranks and resumed on 1 checks the adapted 512 rollout rows. `tests/owl/train/test_config.py` again loads every `configs/*.yaml`, as in Isaiah's tree.

## Teacher settings (rebuild Task 4.4)

- **Values.** All four configs carry `scaling_6m`'s teacher: `teacher_mode: last_best`, `teacher_kl_coef` and `teacher_value_coef` 0.005, no `teacher_schedule`, `teacher_segments_per_minibatch: 128`, and no `teacher_init`. The chunk size is **not divided by the world size**, although the task text asked for it: Isaiah's per-rank configs keep 128 (`scaling_3m` at 64 envs/rank and `scaling_1p5m` at 32 envs/rank on 2×5090; `winner_ce_6m_4x5090` keeps its 256), and the reviewed Phase 4 brief (`ops/rebuild-2026-09-29/briefs/4-teacher.md` §4) says the same. The chunk only slices the precompute, so the value leaves the targets' math unchanged. Per rank it is `min(128, n_envs)`, so every ranked config computes the whole rollout in one precompute call. If the Task 6.1 smoke shows precompute memory over budget, reduce the chunk; Isaiah does this for large models (32 at 153M+).
- **Refresh and cache.** These are Isaiah's unchanged mechanisms. The teacher is the last-best model, refreshed in place when the student's evaluation win rate reaches 0.7 at each `checkpoint_freq` (10M global env steps since the owner's 2026-09-30 decision, about every 610 iterations; 20M before). The periodic checkpoint and this evaluation share that one interval. Its FP32 targets are precomputed once per update and cached for the rollout: `rows × TEACHER_TARGET_BYTES_PER_ROW` (102,208 B). `ForwardWorkload` gains `cached_teacher_rows`, and the teacher-chunk headroom line reports `teacher_chunk_bytes` and `teacher_cache_bytes`: 1,674,575,872 B at 2 ranks, 837,287,936 B at 4 and 418,643,968 B at 8, the same per chunk since one chunk covers the rollout. A cache smaller than its chunk is rejected.
- **Teacher checkpoint source.** No config holds a checkpoint path. The source is an explicit launch input: `--load-model-weights CHECKPOINT` (the BC best, which seeds the student and the last-best teacher) or `-o rl.teacher_init=CHECKPOINT`. `_require_kaggriculture_teacher_source` in `scripts/run_ppo.py` runs before the workload check. It rejects a fresh Kaggriculture `last_best` launch that names neither, with an error naming both inputs and `-o rl.teacher_mode=null`. Separately, it rejects a `teacher_init` that is not a file, with an error naming the missing path. On a scratch launch Isaiah's rule silently leaves the teacher off until the first promotion, and Task 6.1 needs the teacher on. Orbit launches and resumes, which restore the run's own last-best, keep Isaiah's rules.
- **Tests.** `test_teacher_settings_are_scaling_6ms_last_best_teacher` names the six fields in every Kaggriculture config, as literals and as equality with `scaling_6m`. Separate tests cover the cache bytes per config, a multi-chunk rollout (16-row chunks, 64 cached rows) and the too-small-cache rejection. The `run_ppo.main` startup tests pin the bytes in the printed line, and cover the missing-source error (no run directory and no headroom lines), `teacher_init` as a source for the CPU and 8-rank configs, a missing `teacher_init` file, `teacher_mode=null` (no teacher-chunk line), and Orbit/resume exemption. The earlier startup tests now pass a placeholder `--load-model-weights`.
- **Checks.** Seven mutations were each applied, run and restored byte-for-byte (`ops/rebuild-2026-09-29/teacher-configs-4.4/mutations.log`). The 4-rank KL coefficient changed to 0.001 failed 3 tests. The 2-rank chunk divided to 64 failed 6. Dropping the source check failed 2, and dropping the `teacher_init` existence check failed 1. Cache rows set to chunk rows failed 1. The W&B mutations are recorded in the [[ppo-runs-publish-kaggriculture-telemetry-to-the-v3-wandb-project|W&B Reference]]. `just py-prepare` passed with 1,712 passed and 11 skipped, and docs-fresh passed (`teacher-configs-4.4/py-prepare.log`).

## Limits and handoffs

- **Launch after the check.** Since the Task 3.1 remainder (`15ea55f`) `require_orbit_env` is gone and `run_ppo` builds the native env and trains through the shared path ([[ppo-trainer-seams-map-any-schema-and-alarm-on-replay-drift|trainer seams Reference]]). Since Task 3.1 verify r1 the 2/4/8-rank configs set `eval_replay_games: 0`, because a positive count fails at startup until Task 7.3; `test_ranked_config_optimizer_and_ppo_equal_scaling_6m` pins that this and the per-rank minibatch are the only PPO differences from `scaling_6m`, and the `run_ppo.main` startup tests now pass the shipped presets without an override. Their headers say they train through the shared path. The native env computes rewards from this schema in unit tests; no training run has used it.
- **BC is not checked.** The BC trainer (Task 5.2) does not exist yet; it must add its batch as a `ForwardWorkload` through the same check.
- **The trunk bounds are conservative.** Trunk headroom is a lower bound and trunk calls an upper bound, from full padding. Evaluation uses the `n_envs × 2` upper bound.
- **Chunking is timed on the GPU, not verified there.** Teacher chunks rely on the model's chunking. The [[model-only-sps-ceiling-bounds-per-rank-throughput|model-only SPS ceiling]] run at `e1458d2` counted 1, 2 and 3 trunk chunks for a 16,384-row teacher proxy at sparse, mid and dense densities, as the guard predicts (see the [[compiled-gemm-template-overflows-above-2-21-rows|overflow Reference]]). That was timing only: no numerical-correctness comparison was retained, the proxy is not the real teacher path, and the production teacher integration and these configs' own chunking remain CPU-tested only.
- **Pending dependencies:** restoring `scaling_6m`'s `eval_replay_games: 8` needs Task 7.3's Kaggriculture replay export. The teacher settings are pinned (Task 4.4); since the Task 3.1 remainder a teacher-on run needs only its launch-time teacher checkpoint (`--load-model-weights` or `rl.teacher_init`).
- **Teacher cache and chunk memory are unmeasured on the GPU until Task 6.1.** The cache bytes are arithmetic from the target shapes, not an allocator reading.
- **Memory is unmeasured.** The spm 8 / accumulation 1 split holds only if the Task 6.1 memory smoke confirms it; otherwise the plan moves to 4 / 2 with the same product. The 8-rank shape (32 envs, spm 2) is qualified only by Task 6.3b on an owner-approved 8-GPU pod.
