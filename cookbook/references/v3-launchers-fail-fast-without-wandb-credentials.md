# v3 launchers fail fast without W&B credentials (run_ppo; train_bc pending)

**Adaptation.** The owner's request: "make sure all v3 experiments wired to w&b." Before this change, Isaiah's `run_ppo` logged to project `orbit-wars` with no v3 identity. It found a missing key only inside `wandb.init`, after config, env and model setup. Its `--log-mode debug` outage was silent. The BC trainer's `--wandb-mode offline` was just as silent, and its one real run was never reported as offline. The audit and per-entry-point table are in `ops/rebuild-2026-09-29/wandb-audit.md`.

**Scope.** This change covered every v3 launcher then on integration (`kg/isaiah-gap-closure`, merged into this branch at `994818b`); `scripts/run_ppo.py` was the only one. `scripts/train_bc.py` reached integration later, with the Phase 5 BC landing (`kg/merge-bc-c`), and has not adopted the gate, the explicit offline flag or the receipt; that adoption is the next step in this same workflow (see Limits).

## What changed (branch `kg/rebuild-wandb`)

- **`python/owl/train/logging.py`** is extended in place. Isaiah's `LogMode`, `MetricLogger`, `DebugLogger`, `WandbLogger`, `create_logger` and `close(exit_code=...)` are kept.
  - **Project.** `WANDB_PROJECT = "kg-v3"` for every run launched from this repository, Orbit or Kaggriculture; the `game` tag separates them.
  - **Mode and gate.** `WandbMode` (online/offline) and `LogMode` resolve to a `TelemetryMode` (`wandb-online`, `wandb-offline`, `disabled`).
    - `check_telemetry` is the startup gate. Online requires `wandb_credential_source`, which mirrors wandb 0.26.1's lookup: a set `WANDB_API_KEY`, which must be neither blank nor padded, else a password in the `NETRC` (default `~/.netrc`) entry for the `WANDB_BASE_URL` host (default `api.wandb.ai`). Otherwise it raises `MissingWandbCredentialsError`, whose message names the pod workflow, `WANDB_API_KEY`, `--wandb-mode offline` and `--log-mode debug`.
    - `WANDB_BASE_URL` must be http(s) with a host and no embedded credentials; a set but empty value is rejected rather than read as the default. It is checked before any key source.
    - In either W&B mode, online or offline, the gate also validates `WANDB_BASE_URL` and rejects a set `WANDB_API_KEY` that is blank or padded. wandb 0.26.1 rejects each of these inside `wandb.init(mode="offline")` (`claude-verify-wandb-r1` F1, re-probed after the fix). Debug logging never starts wandb and checks none of them.
    - After those checks, the gate runs the installed wandb's own `wandb.Settings(base_url=...)` and `wandb.Settings(api_key=...)` validators, which `wandb.init` applies in every mode (`claude-verify-wandb-r2` R1). This rejects addresses such as `https://wandb.ai`, `http://api.wandb.ai`, `https://app.wandb.ai` and `https://ho st.example`. The error names only wandb's error type, since wandb's messages quote the value. Other W&B settings are not pre-checked.
    - A malformed netrc or URL raises without quoting it.
    - A set `WANDB_MODE`, even an empty one, that disagrees with the flag is rejected. This is stricter than wandb: `wandb.init(mode="offline")` with `WANDB_MODE=online` or `disabled` silently starts an offline run, because init arguments override the environment; only an empty value raises (`claude-verify-wandb-r3` P3-1, re-probed on wandb 0.26.1 in `ops/rebuild-2026-09-29/wandb-2026-09-29/wandb-mode-probe.log`).
    - Offline and disabled print a `W&B TELEMETRY OUTAGE` banner to stderr.
  - **Identity and receipt.** `RunIdentity`, `plan_attempt`, `record_attempt` and `read_attempts` keep one strict-schema JSON record per launch or resume in `<run_dir>/attempts.jsonl`. `read_attempts` checks each field's type and value, the attempt order, a constant experiment id and job type, and the source-commit history. The record holds the attempt, experiment id (explicit or the run directory name; resumes keep it), job type, source commit (`git HEAD`, `-dirty` for tracked edits; `--source-commit` only where git metadata is missing, and rejected when it disagrees with git, via `resolve_source_commit`) with all earlier ones, config SHA-256 (canonical JSON), `telemetry_mode`, W&B project, entity, run ID and URL, start env steps, and a timezone-aware start time.
  - **Observed mode.** `WandbLogger` compares the started run's `offline` and `disabled` flags with the requested mode and closes the run and raises on a mismatch (for example, an SDK downgrade to a no-op run), so `telemetry_mode` in the receipt is the mode the run used.
  - **W&B run shape.** The W&B run is named `<job type>-<run dir>` (`ppo-<run dir>` for PPO), grouped by experiment id, typed by job, and tagged `kaggriculture-v3`, job and game. It stores `v3.experiment_id` and `v3.job_type` in its config, which stays constant on resume, and the `v3/*` attempt fields in its summary.
  - **Reuse.** `create_metric_logger` takes a launcher's own config and game, so BC and future probes can reuse the same path.
  - **Pod copy.** `wandb_netrc_entry` returns only the explicit `machine <W&B host>` netrc entry, and `scripts/export_wandb_netrc_entry.py` pipes it to a pod (it refuses a terminal).
- **`scripts/run_ppo.py`** stays the one trainer.
  - It adds `--wandb-mode`, `--experiment-id` (fresh launches only) and `--source-commit`.
  - The gate is the first step inside the distributed session, on rank 0, before config load. Non-main ranks only resolve the mode.
  - Rank 0 plans the attempt once the run directory exists, before env or model setup. That rejects a resume without receipts before `VectorizedEnv` is built (tested). It records the attempt immediately after the logger opens, inside the failure-closing logger session, and prints the receipt path again on an outage.
  - `_validate_args` rejects offline mode combined with debug logging, and an `--experiment-id` on resume.
- **`README.md`** documents the gate, the flags, the receipt and how to resume an offline run.
- **Pod procedure.** [[../workflows/install-the-wandb-credential-before-any-pod-launch|Install the W&B credential before any pod launch]].

## Landing merge with Task 3.1's logger (2026-09-30)

Task 3.1 (landed first, in the [[ppo-runs-publish-kaggriculture-telemetry-to-the-v3-wandb-project|PPO W&B project Reference]]) had its own `--wandb-mode` flag and `wandb_init_identity`: Kaggriculture to `kg-v3` as `ppo-<run dir>` with group `ppo`, Orbit to `orbit-wars` with Isaiah's arguments, offline rejected on resume and with debug logging, and a printed offline line. ## Limits and gaps

- **No live run.** No live W&B run was created, and no pod or GPU check ran. The gate proves that a key is present, not that it is valid; the pod workflow's `wandb.Api()` check covers that.
- **Kaggriculture runs only on CPU tests so far.** Since the landing merge, Task 3.1's Kaggriculture launch runs through the gate and receipt; its resume tests carry an `attempts.jsonl`, and the offline-banner `main` test reaches the run directory. No real Kaggriculture launch has written a receipt yet.
- **BC lags after its landing.** `scripts/train_bc.py` is on integration since the Phase 5 BC landing (`kg/merge-bc-c`) and still uses `owl.train.bc.create_bc_logger`: it has not adopted the gate or the receipt, accepts offline silently and fails late without a key. Its adoption (`check_telemetry` before data load, an explicit logged offline mode, `telemetry_mode` in each attempt receipt, the shared logger) is the step that runs right after the BC landing in this same workflow; the steps are listed in the audit.
- **Other entry points.** The Orbit benchmark scripts and the frozen, checksummed ops probes are unchanged and log locally. A future Kaggriculture evaluation harness must use the contract.
- **Offline resume is rejected.** wandb 0.26.1 ignores `resume` in offline mode and would start a new same-ID offline segment, so resume launches reject `--wandb-mode offline` (Task 3.1's rule, kept by the landing merge). A run whose attempts were offline must be synced before an online resume; that sync-then-resume sequence has not run live.
- **Old runs.** A resume needs `attempts.jsonl`, so run directories created before this change cannot resume under the new code. No v3 PPO run exists yet.
