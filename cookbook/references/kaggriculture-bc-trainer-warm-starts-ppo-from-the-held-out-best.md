# Kaggriculture BC trainer warm-starts PPO from the held-out best

Plan Task 5.2 asks for a BC trainer on the rebuilt model that reuses Isaiah's optimizer factory, BF16 and compile path, keeps the best checkpoint by held-out NLL and stops on sustained held-out degradation (lesson L9). This change builds the trainer script and its tests. The BC run itself waits for the Task 5.1 shards and the pod.

## Adaptation inventory

- `scripts/train_bc.py`: CLI in `run_ppo.py`'s shape (fresh `CONFIG --data --output-dir`, restart from a run directory, `torchrun` for several GPUs, `--log-mode`, `--wandb-mode online|offline`, `--max-runtime-hours`, `--source-commit`). It runs the GEMM workload check for the BC microbatch and validation forwards and the compile-stack check. It then builds the model with `create_model` and `reset_parameters`, compiles through `configure_model_compile` (the Kaggriculture cuBLAS-only claim), builds the optimizer with `create_optimizer` / `create_lr_scheduler` and wraps it with Isaiah's DDP adapter.
- `python/owl/train/bc.py`: `BCConfig`, the objective, `TrainSharding`, `HeldOutSelection`, checkpoint and resume state, a W&B logger (project `kg-v3`, `job_type` `bc`) and `train_bc`. BF16 comes from the PPO config's `rl.dtype` through `autocast_context`. The model, dtype and compile settings come from the PPO config that BC warm-starts (`ppo_config`), so the BC checkpoint matches that PPO run's model. `wrap_bc_model_for_distributed` casts the model for Isaiah's Orbit-annotated DDP adapter, whose dispatch passes Kaggriculture batches through unchanged. The Task 3.1 trainer seam has not generalized those annotations yet.
- `python/owl/kaggriculture/bc_data.py`: the shard writer and loader. `configs/bc/kaggriculture_2rank.yaml`: the 2-rank BC config for `configs/kaggriculture_2rank.yaml`. It sits under `configs/bc/` because the existing config tests load every top-level `configs/*.yaml` as a PPO `FullConfig`. `README.md` has a new "Kaggriculture BC warm start" section.

## Decisions made here

- **The critic is trained, not frozen.** Isaiah trains all of the shared trunk and both heads together, and his teacher distillation weights policy KL and winner CE equally (`teacher_kl_coef = teacher_value_coef`). BC is distillation from the recorded player. So the loss is the turn NLL divided by program length, plus `value_coef` (1.0) times the per-seat winner CE against the episode's raw final banks (L1: the larger bank wins, a draw is 0.5 each). The reference froze the critic head, but its trunk still moved, so its critic reached PPO miscalibrated with no target. A test shows that a policy-only loss leaves the four `critic_head` tensors without gradients. Isaiah's adapter builds DDP without unused-parameter detection for this model, so the joint loss also gives every parameter a gradient. DDP itself was not run. Isaiah's own recipe used no imitation learning (`docs/write-up.md`); BC here is the plan's owner-required addition.
- **Shard format.** The loader follows the refreshed 5.1 brief (branch `kg/rebuild-bc-brief` at `bcefd02`, still awaiting Codex review). Shards are `kaggriculture-bc-shard-v1`: one `np.savez_compressed` per episode at `<split>/<day>-<episode_id>.npz`, with the 28 observation fields, `can_act`, `tokens`, `lengths`, `turn` and a `schema` id. The brief lists the manifest's contents but not its key names. The loader requires `schema`, `observation_schema_version`, `contract_document_version` and per-episode `episode_id`, `split`, `terminal_banks`, `admitted`, `shard_path`, `shard_sha256` and `shard_bytes`. It keeps other custody keys uninterpreted. Task 5.1's `prepare.py` must emit these names, or use `write_bc_episode` / `write_bc_manifest`.
- **Residency and sharding.** Each rank keeps rows `[rank::world_size]` of every episode in host memory (the reference's split). Exact integers are stored as range-checked int32 and tokens as int16, then gathered back as int64. Loading verifies every shard's SHA-256, byte count and schema id, and runs the full `check_contract` once. Training order is a permutation seeded by `(seed, epoch, rank)` over that rank's rows, so restarting from `bc_state.pt` repeats the uninterrupted run. Every evaluation covers all validation rows. A preflight pass admits every training program through `evaluate_actions` before step 1.
- **Selection and stopping.** Each evaluation's held-out NLL feeds `HeldOutSelection`. The lowest is written as `checkpoint_bc_best.pt`, with a SHA-256 record in `checkpoint_bc_best.json`. Training stops after `patience_evals` evaluations with no new best, at `max_steps` or at the runtime cap. `bc_history.jsonl` holds the NLL curve and `bc_result.json` the stopping step and reason. The best checkpoint has exactly `run_ppo.py`'s keys with `env_steps` 0, next to the PPO `config.yaml`.
- **Starting values** in `configs/bc/kaggriculture_2rank.yaml` are not measured. They are the PPO config's Muon/AdamW values with the cosine over `max_steps`, 256 turn rows per rank per step, `max_grad_norm` 10, evaluation every 200 steps and patience 10. The run statement has to name any change.

## Checks

- `tests/kaggriculture/test_bc.py` (18 tests) uses tiny CPU models and synthetic shards whose programs a second tiny model sampled. The tests cover:
  - the shard round trip at contract dtypes, and rejection of a tampered hash, a duplicate episode, an old `features/context` shard, a missing split, unpaired rows and out-of-range compaction;
  - the loss halving on a memorizable batch, and every parameter receiving a gradient;
  - two fake ranks holding disjoint rows that cover each split, with deterministic per-rank order;
  - a scripted evaluator that selects the best checkpoint and stops, with the best weights equal to the step-1 snapshot;
  - a restart from `bc_state.pt` that matches an uninterrupted run bit for bit, and a resume that rejects a different dataset or world size;
  - the best checkpoint loading through `run_ppo`'s `_load_model_from_checkpoint`, `_load_model_weights` and PPO's `_checkpoint_metadata`;
  - the 2-rank BC config targeting the 2-rank PPO config;
  - the script running fresh and resuming on CPU.
- Mutation checks (`ops/rebuild-2026-09-29/5.2/mutations.log`) killed 11 of 12 mutants. The survivor shares one permutation seed across ranks. The rank partitions are disjoint, so it changes no row set.
- `just py-prepare`: 1,691 passed, 11 skipped, docs-fresh clean (`ops/rebuild-2026-09-29/5.2/py-prepare.log`).

## Limits and open dependencies

- Nothing has run on a GPU yet: no BF16 autocast, compiled trunk, DDP/NCCL, pinned-memory transfer or live W&B. The owner's Mac ran FP32 with no compilation. Throughput, peak memory and load time are unmeasured: each rank decompresses every shard, gathers on the host each step, and `clip_grad_norm_(error_if_nonfinite=True)` syncs once per step. Host memory per rank for the real slice is unmeasured too.
- The BC run needs the 5.1 shards. Their token half waits on the Task 1.4 `kaggriculture_encode/decode` binding, and the full-slice run needs a machine that can read volume `4llk4uaf20`. It also needs the pod and FlashAttention, because `configs/model/kaggriculture.yaml` forces it (plan 6.0). PPO from the BC best then needs `run_ppo.py` to run Kaggriculture (Tasks 1.4/3.1). Today only its loaders are exercised.
- The synthetic fixture uses one `make_obs` env per row. Multi-env `make_obs` batches with small actor counts can draw a lifespan below the −1 sentinel and fail `check_contract` (seen with 4–5 envs), which is a limit of the test fixture.
